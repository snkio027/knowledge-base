# Knowledge Base 资产与归档约定

本约定细化[项目架构](architecture.md)中的身份、字段来源、检索缓存和归档边界，用于后续最小工具实现。示例是拟议数据形状，不是已登记资产、已冻结 Schema 或可执行命令。首期只实现明确需要的字段，不建立覆盖所有文档类型的通用模型。

## 1 身份与字段

`catalog/registry.json` 拟保存 `schema_version`、逻辑命名空间 `knowledge-base` 和资产卡的相对路径清单。逻辑命名空间只定义一次，不随本地文件夹或 GitHub 仓库名称改变；与 `asset_id` 共同确定全局身份。资产卡中的 ID 在该命名空间内唯一，历史 ID 可以作为显式别名，但有歧义时不得自动选择。

已有 Document ID 可以作为当前维护成果的资产 ID。若历史原稿和维护稿声明同一个 Document ID，却不是同一维护对象，应分别登记资产身份并保留原声明与来源关系；不能改写原稿 Front Matter，也不能把历史出现过的 ID 都加入“当前维护文档唯一性”判定集合。

以下是 ESD Reference 的拟议资产卡，路径对应现有文件，卡本身尚未建立：

```json
{
  "schema_version": 1,
  "asset_id": "ESD-REFERENCE-001",
  "kind": "document",
  "canonical": {
    "root": "content",
    "path": "design/02-优秀系统设计-从约束不变量到证据-v1.1.0.md"
  },
  "purpose": "reference",
  "topics": ["system-design"],
  "maintenance_status": "maintained"
}
```

资产卡不手工复制标题、文档版本或稿件状态。解析器只支持事先声明的 ESD、C++ 元数据位置；没有适配规则返回 `unknown`，相互矛盾的声明返回 `conflict`。`maintenance_status` 初期仅表达 `maintained`、`archived` 或 `unknown`，不参与技术接受或正式发布判断。

| 数据 | 权威 | 派生视图中的必要来源信息 |
| --- | --- | --- |
| 资产 ID、用途、主题、当前入口 | 资产卡 | 卡路径与卡摘要 |
| 标题、版本、稿件状态 | 正文的已声明元数据位置 | 文件摘要、解析规则版本及字段位置 |
| 文件大小与摘要 | 本次读取的文件字节 | 根别名、相对路径和读取结果 |
| 制作、审核、发布事实 | 原始证据记录 | 证据摘要、引用位置和适用对象 |
| PDF 页文本 | 提取缓存 | PDF 摘要、提取器与参数、物理页号 |

来源元数据无法解析时，目录仍可按路径、摘要及人工资产身份找到文件，但不能显示猜测的版本。文件名差异可以提示，不自动修正文或改名。

## 2 修订与关系

单文件修订绑定 SHA-256，Git commit 与路径补充定位信息。多文件资产应列出完整的声明文件集合及逐项摘要；若已有出版输入清单，则引用该清单及其摘要，不另造一个 preparation ID。集合完整只表示声明的文件齐备，不等于编译器运行时依赖已经完整封闭。

关系采用显式目标引用，例如“源自某原稿”“此 PDF 表现某内容修订”“此审核覆盖某制品”。用于审核、出版或决策证据的关系必须绑定固定摘要或固定证据集合，不能只有可漂移的 `main` URL。仅用于当前阅读导航的关系可以指向当前资产入口，但必须与证据引用区分。

审核结论保留原审核者、范围、目标字节和限制。正文改变后，旧结论继续描述旧修订；目录可以显示新修订尚未关联审核，不将旧记录改成失败或自动转为新修订通过。文件重命名但字节相同时，更新定位关系即可，仍需确认审核范围是否包含文件间结构。

## 3 路径与写入权限

本机配置将 `content`、`archive`、`cache` 等根别名映射为绝对路径；公共资产卡不保存个人主目录。根映射是部署配置，不属于资产身份，但应随恢复说明受控保存。出版工作区由独立引擎管理，不借目录配置绕过其限制。

所有输入必须先校验再打开：相对路径不得包含绝对路径、驱动器前缀或 `..` 越界；逐级检查符号链接；对大小写和 Unicode 等价名称报告碰撞。首期归档导入拒绝符号链接及非普通文件，不使用指向源文件的硬链接保存制品；源文件即使有硬链接，也只复制并核对独立字节。

缓存、归档暂存区及最终归档根不得与内容 checkout、产品输入或活动引擎输入重叠。先解析真实路径并检查祖先关系；不只用字符串前缀判断。首期按单写入者运行；发现目标存在或上下文不支持时失败关闭，不承诺抵御同账号恶意并发替换所有文件系统对象。

| 拟议动作 | 允许写入 | 不允许写入 |
| --- | --- | --- |
| `scan` | 配置的缓存、扫描报告 | 正文、资产卡、历史记录 |
| `check` | 显式指定的检查报告 | 自动修正文、自动更改状态 |
| `search` | 无；缓存更新须显式触发 | 按查询结果移动、去重或删除文件 |
| `ingest` | 归档暂存区、不可覆盖的最终包、导入记录 | 原包、源文档、冻结清单和已有发布事实 |

资产卡由维护者确认后编辑并提交。工具不自动 `git add`、提交、推送或发布，导入也不获得整理用户未跟踪材料的权限。

## 4 盘点和检索缓存

扫描配置明确根、包含规则、排除规则及未跟踪／忽略文件策略。`.git`、凭证和运行环境应排除；历史忽略制品与未跟踪原件是否纳入必须明确列出。默认搜索范围不能冒充完整盘点范围。

每次扫描记录枚举范围、开始与结束时间、文件集合及错误。文件读取前后若大小、时间或身份变化，标记该项不稳定，重试或保留失败，不发布为一致快照。盘点是可重做的观察结果，不替代出版引擎的冻结输入。不能读取的目录、部分失败和中断都要反映到整体覆盖状态。

PDF 文本缓存键由原 PDF SHA-256、提取器名称与版本、提取参数共同确定。每页记录从 1 开始的物理页号；印刷页码标签另存，不混用。结果包含匹配片段、原件位置及摘要。查询时发现原件摘要变化，应将缓存标为过期而不是返回看似当前的命中。

提取状态至少区分 `extracted`、`empty_text`、`failed`、`not_attempted`；混合 PDF 的单页失败或空文本不能隐藏在整本“成功”之下。缓存丢失可重建，原始文件、资产卡、归档包与原始审核证据不可由缓存恢复。

## 5 归档包

归档导入先保存收到的实际字节，再解释其身份。内部文件名和布局遵循包内相对路径，不依赖原机器的绝对目录。原证据含旧路径时保留原文，在外层记录定位映射；不得直接跟随其中任意本机路径读取其他文件。

```text
archive/<asset-id>/<package-id>/
  README.md        包的用途与恢复提示
  manifest.json    外层文件清单
  artifacts/       原制品字节
  evidence/        原 manifest、审核、授权或回执
  sources/         实际收到的来源文件，可缺省但必须声明
```

`asset-id` 的目录表示必须经过安全编码或采用校验通过的标识，不能直接把任意用户字符串拼成路径。外层清单包含协议版本、资产引用、接收类型、来源可用性，以及每个成员的 `path`、`role`、`bytes`、`sha256`。文件按包内路径排序；完整枚举必须同时检查缺失项和额外文件，不能只验证清单所列文件。

`package-id` 是目录层的内容身份，不是引擎构建或发布身份。拟采用 SHA-256，输入为版本化、规范序列化的包描述：资产引用、接收类型、来源可用性和排序后的成员列表；不含接收时间、本机路径、`package-id` 或清单自身摘要。规范序列化规则与测试向量须在首次实现时一并固定，不在实现前声称已有稳定包 ID。

外层清单不把自己的最终摘要写回自身。所有 README、来源及证据文件作为成员被绑定；清单的摘要由外部导入记录或备份验证记录保存。后续补到新的来源文件或审核材料时形成新包或独立关联记录，不往旧包里追加字节。

来源可用性区分“声明输入集合完整且匹配”“仅收到部分来源”“未提供来源”。缺少来源的历史 PDF 仍可作为受限历史资产归档，但不得通过“来源完整”验收。`WORKTREE` 候选有完整实际输入快照时不被一律拒绝；只有 Git commit 或文件列表时不得宣称可恢复当时工作树。

## 6 导入提交点与失败行为

导入使用与最终归档同一文件系统上的独立暂存目录，按以下顺序处理：

1. 校验根、路径、协议版本和目标类型；拒绝不支持的文件系统条件。
2. 复制实际收到的普通文件，核对预期摘要，保存原始证据字节。
3. 生成外层清单，核对全文件集合、大小和摘要，并完成约定的文件与目录同步。
4. 以不替换已有目标的方式提交整个包。已有同 ID 包先完整核对，一致则幂等返回，不同则报告冲突。
5. 提交后追加接收记录，之后才更新可重建目录与检索缓存。

包可见性的原子提交与断电持久性是两项不同保证。实现必须明确提交点、所支持文件系统、提交后的目录同步及异常行为，并通过故障注入验证；不能把普通覆盖式重命名当作“不覆盖提交”。提交前失败或取消不得留下可识别为成功的最终包。

提交后若导入记录或缓存更新失败，保留已提交包，报告“包已提交，后续登记失败”，重试从包内清单对账；若持久化确认失败，报告状态未确认并保留现场，不再生成矛盾的失败终态或无条件成功记录。这里不承诺归档、Git、备份和远端发布之间的跨系统事务。

已有出版证据的语义不随归档提交改变。`package verified` 只说明接收和文件核对，不能替代 `content accepted`、`release authorized` 或 `released`。

## 7 备份与公开边界

备份范围覆盖正文、资产卡与 Schema、必要 Git 历史、未跟踪原件、归档包和恢复配置。可重建缓存可以排除，但不得仅按 `.gitignore` 排除所有历史忽略资产。备份目标不位于被备份目录内部；目标位置、加密凭证、保留策略及恢复人需要实施前确认。

一次合格演练必须记录精确备份快照、恢复到空目录后的完整包文件集合及摘要、实际打开检查的文件，以及失败或未测项。原件恢复与历史重新编译分别报告。不能把 `check` 退出成功、仓库仍能 clone 或 PDF 能打开中的任何一项单独作为全部恢复证明。

公开的目录可以只保留受控资产的稳定身份和访问限制，但不能泄露私人根路径或敏感内容。需要脱敏时保存受控原件与原摘要，另登记脱敏副本和处理说明；不得静默替换已发布载荷或将脱敏件登记为原始字节副本。
