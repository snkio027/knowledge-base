# Knowledge Base 架构设计

Knowledge Base 是面向高级工程师的知识内容仓库，承载系统工程文档、技术手册、可运行实验及其验证记录。它还保存这些内容形成出版物后的发布事实和历史资产，但不再承载活动出版工程。架构的核心是：**开放文件是内容主源，Git 保存变更历史，独立出版引擎生成制品，轻量目录帮助定位，归档与备份保证可恢复。**

本设计在现有仓库边界上增加资产管理方案，不重做已经分离的出版系统。资产卡、目录工具、检索缓存和归档导入均为拟建能力；文档完成不等于这些能力已经实现。数据细节见[资产与归档约定](asset-contract.md)，交付顺序和验收反例见[实施与验收计划](implementation-plan.md)。

## 1 目标与范围

项目首先服务于阅读、学习和工程回查，而不是文件管理本身。读者应能从主题导航找到正文，从论述找到实验与证据，从 PDF 找到对应的内容版本；维护者应能解释一份材料的身份、来源、审核范围和恢复方式。

首期资产能力解决三个具体问题：文件散落时仍能找到；文件重命名或正文继续演进时不混淆身份；旧成果需要恢复时有确切字节和证据可用。采用开放文件、少量 JSON 资产卡和现成工具，不要求先给所有文件补齐分类。

本设计不包含网站、多人工作流平台、通用知识图谱、向量数据库或新的 PDF renderer。它不扩大正文技术验收，不修改已发布 PDF，不启动新的发布，也不因整理目录而自动删除重复文件。实施环境限定为本机 macOS，新增 Python 工具由独立 uv 项目管理。

## 3 职责与数据流

两个仓库之间传递的是显式输入和可核对的证据，不共享可变运行环境。拟建目录工具是知识库的辅助工具，不是出版引擎的另一个入口。

```text
knowledge-base                         publication-engine
正文 / 实验 / 内容验证                  产品配置 / adapter / layout / engine
          │                                      │
          └──── 显式内容 checkout ────────────────┤
                                                 ↓
                                  专用工作区：快照 → 构建 → 候选
                                                 │
                        制品 + 实际输入快照 + 已有证据
                                                 ↓
拟建资产目录：核对与关联 ─────────────→ 外部 archive：原字节归档
          │                                      │
          ↓                                      ↓
外部 cache：盘点 / PDF 文本 / 派生目录       备份介质 → 空目录恢复

授权与实际分发 → knowledge-base 发布记录 → 目录只引用事实
```

**内容层**负责论述、实验、编辑规范及内容审查。对具体字节的接受不自动覆盖后续修改；原有验证记录保留当时的工具链、平台和未验证范围。目录不得把实验 `PASS` 汇总成整章正确，更不能从 PDF 生成成功推导出性能或并发结论。

**产品与引擎层**负责从声明的内容输入生成阅读制品。知识库只通过受支持的外部入口使用它，不导入引擎私有 Python 模块，不保留兼容构建脚本，也不重新实现输入冻结、候选状态或发布授权。

**资产层**负责稳定身份、当前位置与必要关系；**归档层**负责保存指定包的确切字节；**检索层**负责从原件生成可丢弃的查找视图；**备份层**负责在原存储不可用时恢复。归档不是异地备份，搜索索引也不是内容主库。

## 4 内容和资产的权威来源

### 4.1 文件盘点与资产登记

文件盘点（inventory）覆盖显式配置的范围，记录根目录别名、相对路径、大小、摘要和读取结果。它可以发现未登记文件、重复字节或提取失败，但不能自行决定某个文件是什么业务资产。

资产登记（registry）只覆盖人工确认的长期成果。首期选择 20–30 个代表性资产，不以“所有文件都有资产卡”为上线条件。一本手册可以关联正文、PDF、原始附件和实验；单个文件也可以暂时只有盘点记录。

文件路径是位置，资产 ID 是逻辑身份，SHA-256 是字节身份。三者不可互相替代。移动文件只更新位置；修改正文产生新的修订绑定；相同摘要仅表明字节相同，不授权合并原件、维护稿或交付副本。

### 4.2 六类身份共用小模型

| 身份 | 回答的问题 | 最小绑定 |
| --- | --- | --- |
| Asset | 长期维护的成果是什么 | 稳定资产 ID 与当前入口 |
| Revision | 指的是哪一份内容 | 文件摘要或明确文件集合；可附 commit 与路径 |
| Rendition | 这份 PDF 与哪份源内容对应 | 原制品摘要及有证据支持的来源关系 |
| Production | 如何制作这份制品 | 原构建、attempt、输入绑定和工具记录的引用 |
| Review | 谁接受了什么范围 | 被审字节、审核范围、结论与原始意见 |
| Release | 哪些字节实际获准分发并已分发 | 授权、载荷、tag 和分发回执 |

这六类语义不要求六套服务或操作界面。资产卡、不可变归档包和现有证据足以表达首期关系。缺少某类证据时保留缺项，不根据名称补齐。

### 4.3 字段只能有一个维护权威

标题、文档版本和稿件状态来自已支持的正文元数据约定；稳定资产 ID、用途、主题和维护状态由资产卡管理；制作、审核及发布结论来自对应的原始记录。缓存只保存读取结果及其来源，不反向覆盖这些权威。

例如，现有 ESD Reference 的文件名含 `v1.1.0`，正文 Front Matter 声明 `2.0.0-draft.1`。目录应读取正文并提示命名差异，不能为了“统一”改写原件，也不能让文件名优先于正文。无法解析的格式标记 `unknown`，两处权威声明冲突时标记 `conflict`，由维护者处理。

`maintenance_status: maintained` 仅表示仍在维护；它不意味着 `BASELINE`、已审核或已发布。原始附件可以保留历史 Document ID，但不因此成为当前维护入口，具体唯一性范围见[资产与归档约定](asset-contract.md)。

## 5 关键工作流

### 5.1 内容演进

内容通过现有主题入口编辑和验证，提交后形成新的可定位修订。审核结论绑定本次声明的字节和范围；无关的历史证据不追写摘要。如果只有位置改变而字节未变，可以保留原证据绑定，但路径迁移和链接仍需核对。

继续使用各系列自己的质量标准，不用统一资产模板重写正文。[ESD 项目计划](../design/project/plan.md)与[C++ 导航](../c++/README.md)各自负责本领域；本架构只规定跨领域的存储、身份及交接关系。

### 5.2 出版证据接收

目录读取已有 `source-set.json`、`input-bindings.json`、候选清单或发布清单，先识别协议版本，再核对包内实际文件。无法识别的证据可以作为原始附件保存，但不能报告为已解析、已验证的出版关系。

有实际输入快照的 `WORKTREE` 制品可以归档。仅有 `HEAD + dirty` 或清单中的文件名，不能证明当时来源已保存。归档应分别表达“文件摘要匹配”“声明输入集合齐备”“来源关系已核对”，不能用一个绿色状态替代它们。

候选导入只增加“已归档候选”事实。发布清单也不能独自证明上传成功：现有 [FM 发布清单](../publication/releases/cpp-failure-model/v1.0.0/distribution/release-manifest.json)明确将载荷与分发回执分开。目录沿用这个区分，不给历史包补造批准或发布状态。

### 5.3 查找与回到原件

找资产时按 ID、别名、主题和已登记关系检索；找内容时先对 Markdown、代码和 PDF 提取文本做字面量搜索。ripgrep 的 `-F` 可保留中文短词及 `std::atomic<int>` 一类符号的字面含义；其默认忽略规则不能作为完整盘点策略。[ripgrep 使用指南](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md)

PDF 缓存按原文件摘要、提取器版本和参数标识，每页记录物理页序号，搜索结果回到原 PDF 而不是仅显示缓存路径。pypdf 适用于已有文本层的提取，不执行 OCR；空文本或提取失败必须保留为覆盖缺口，而不是“该文档没有内容”。[pypdf 文本提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)

先用 30 条真实查询评价定位正确性、漏检、耗时和过滤需求。只有出现可复现的不足，才考虑 SQLite、复杂提取或其他界面；文件数量本身不是引入索引平台的理由。

### 5.4 归档与恢复

归档包保留原制品、原证据及实际收到的来源文件，外层清单只记录包内路径、角色、大小和摘要。导入先在临时目录完成核对，再以不覆盖方式提交；原始 manifest 不被重新排版或改写。

恢复目标是得到已保存的确切文件，并解释它的来源及验证边界。它不要求所有历史 PDF 都能在新机器上重新构建为相同字节。备份需早于复杂目录建设，至少走通一次“指定备份快照 → 空目录恢复 → 摘要核对 → 打开文件”。普通 `restic check` 与读取实际备份数据的检查不同，后者使用 `--read-data` 等方式；两者都不能替代恢复演练。[restic 仓库检查](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)

## 6 首期组件与部署

首期不运行后台服务，不建立专有数据库主库。下列为目标布局，其中 `catalog/`、`tools/catalog/` 及配套外部位置是拟建部分；现有主题和历史目录不为此搬家。

```text
knowledge-base/
  docs/                 项目架构与数据约定
  design/ atlas/ c++/ zig/  现有内容及内容验证
  publication/          现有历史与书籍发布事实
  catalog/              拟建：registry、少量资产卡、Schema
  tools/catalog/        拟建：独立 pyproject.toml、uv.lock、薄 CLI

本机显式配置的外部位置
  archive/              冻结包，需持久保存并备份
  cache/                盘点、页文本及派生视图，可重建
  publication-work/     独立引擎工作区，不由目录工具接管
```

JSON Schema 结构检查交给 check-jsonschema；项目代码仅补足 ID、路径、关系及元数据冲突等语义检查。Schema 随项目版本化，首期不依赖远程 `$ref`，避免检查结果随网络内容漂移。[check-jsonschema 用法](https://check-jsonschema.readthedocs.io/en/latest/usage.html)

拟建 CLI 只有 `scan`、`check`、`search`、`ingest` 四个动作。它们分别负责盘点、校验、定位及证据归档，不提供 `build`、`approve` 或 `publish`。备份直接使用成熟工具，不包成新的备份框架。

目录工具将拥有自己的 uv 项目与锁文件，不借用出版引擎环境。日常 `uv run --locked` 用于阻止过期锁文件被隐式更新；它不是离线或网络隔离保证，网络策略另行配置。工具具体版本在实施批次锁定，不在设计稿里跟随上游最新版。[uv 锁定与同步](https://docs.astral.sh/uv/concepts/projects/sync/)

## 7 安全与长期维护

目录和归档的输入都按不可信数据处理。读取 Markdown 不执行代码块；解析 JSON/YAML 不执行自定义对象；提取 PDF 不启动文档中的脚本、附件或外部链接。解析任务应有限时、大小和资源上限，失败作为单文件结果记录，不能以不完整扫描冒充完成。

路径采用根目录别名加相对路径，拒绝越界、符号链接逃逸和大小写／Unicode 归一化碰撞。比较时可以检测等价名称，但不能悄悄重命名原件。归档根与缓存根必须与受保护内容、产品及实现输入隔离，具体规则见[资产与归档约定](asset-contract.md)。

本仓库公开，资产卡、证据引用及归档公开前必须检查凭证、私人路径和未授权材料。受控原件与脱敏副本是不同对象；不能用脱敏后的摘要冒充原件。外部根路径、备份密码和恢复密钥不提交到 Git。

Git 远端不是所有本机文件的备份：忽略目录、未跟踪附件及外部归档需要单独纳入范围。备份凭证与恢复说明应在待恢复机器之外可取得。首期不自动执行去重删除、旧包覆盖或备份清理策略。

## 8 取舍与演进条件

选择文件与 Git，意味着放弃数据库的一次性跨对象事务，换取原件可直接阅读、证据可独立核对和工具可替换。选择小型资产卡，意味着一部分材料会长期处于未登记状态；这比自动猜测来源更可靠。选择字面量搜索，意味着先接受有限的排序和语义能力，再用真实查询证明升级需求。

SQLite、图形目录、OCR 和语义检索保留为后续选项，不作为第一版依赖。任何新增索引仍必须可删除后重建；任何浏览器或桌面软件都不是身份权威，也不因“索引外部目录”就获得改写受控文件的权限。

具体实施按能力闭环划批，不按文件或补丁逐项审批。首批先保住文件并验证恢复，再让少量资产走通登记、查找、证据接收和归档。架构验收看能否保持身份与恢复原件，不看分类数量、页面数量或检查数量。

## 9 设计来源与决策边界

本设计综合用户在 2026-10-26 提供的两份同名参考文本及上述固定仓库基线。两份附件逐字节相同，SHA-256 均为 `5ae9ece81cdb90a6b58179a6ab71bf026974f73b356179399b613bc08332ac12`，因此作为同一份设计输入处理。参考稿所引“原方案”未随附，不作为已核验的实施要求。

本轮只建立架构文档并将本地目录由 `kb` 更名为 `knowledge-base`。不实施目录 CLI、备份或归档迁移，不改变出版版本锁定，不修改正文、历史 profile、实验、已发布制品或未跟踪 Zig 材料。后续能力需按[实施计划](implementation-plan.md)确认运行位置及恢复条件后执行。
